# One in-repo generator writes the protocol types for every Language SDK

The types for the pipeline socket are generated from `protocol/schema` by one script, `protocol/scripts/generate.py`, with one emitter per language: Python, Rust, Go and C#. The generated files are committed. This settles the spike ADR 0002 asked for.

## Decision

- **One model, four emitters.** `protocol/scripts/codegen` reads the schemas into a small model (objects, unions, enums, arrays, free JSON), and each emitter writes one file in its language's idiom. Output is deterministic.
- **Same behavior everywhere.** Every type has a decode and an encode (`from_json`/`to_json`, `FromJSON`/`ToJSON`). A value keeps its original JSON, and unknown fields survive a round trip. A constant such as `"type": "ping"` is checked on decode and written on encode, and is not a field. `Message` and `Command` decode by their `type` tag, and a known tag that does not parse, or an unknown one, decodes to an `Unknown` variant that keeps its JSON. Decoding the two unions never fails: it returns a variant or `Unknown`, and never throws or crashes, whatever value it is handed.
- **The model owns the wire-value rules.** `WIRE` and `WIRE_RULES` in `protocol/scripts/codegen/model.py` hold each rule once, as data and as its written definition. Every emitter takes the bounds, the length unit and the depth from `WIRE`, and its runtime preamble only adapts the rule to its host JSON type:
  - **Integer:** the exact decimal value is whole and lies from -2^63 to 2^63-1 (int64), however the token is written: `1.0`, `1e3` and `10e-1` are integers; `1.5`, `1.00000000000000001`, `1e-1000000` and `1e19` are not. A decoder that holds the token as text (Go `json.Number`, a C# `JsonElement`) normalises it to a sign, the significant digits without leading or trailing zeros, and a base-ten exponent, then rejects a negative exponent, more digits plus exponent than the bounds have digits, or a value outside the bounds; Go and C# each implement exactly this in `integerToken`/`IntegerToken`. Python compares the `int`, `float` or `Decimal` it is handed with the bounds exactly. A binary double (Go `float64`, Rust `f64`, a C# `double`) is checked by its own exact value.
  - **Number:** its value as a double is finite. `1e400` is rejected.
  - **String length:** `minLength` counts Unicode code points, so a character outside the Basic Multilingual Plane counts once.
  - **Exactly one:** exactly one of the listed keys is present; a key whose value is null counts as present.
  - **Depth:** a value nests at most 64 levels, the message object being level 1. A union decoder handed anything deeper returns `Unknown` with no fields and does not read below that level, so it never copies or recurses into the rest.
  - **Duplicate keys:** the last value wins. Python, Go and Rust get this from their parsers. C# writes the value once with a writer capped at 64 levels and reads the output once to find repeated keys; only when a key repeats, which `System.Text.Json` cannot read as a `JsonObject`, does it rebuild the tree from that output, keeping the last value of each key.
  - **Unicode text:** a string, or a key, holding a lone surrogate is not valid wire text. A union decoder returns `Unknown` keeping every field. Go and Rust cannot see one (documented limits below).
- **Only the standard library**, plus `serde_json` in Rust. The Python SDK has no dependencies, so the generated Python uses dataclasses.
- **Generated files are committed and never edited.** `task protocol:generate` rewrites them; `task protocol:generate:check` fails when they differ from what the schemas produce, and runs in the protocol gate. Hand-written code sits beside them.
- **Each SDK replays one conformance set.** Every language's own test suite decodes each case in `protocol/examples/decoding.json` (every valid and invalid example, plus edge-case JSON text) through its generated decoder, and checks the variant it decodes to and whether it encodes back unchanged. A case one SDK cannot give the stated outcome for carries a `diverges` marker for that language, and the replay fails once the marker is no longer needed. A marker is either a known divergence still to fix or a documented limit of the host JSON parser, whose reason says so. A Language SDK's CI also runs when `protocol/**` changes.

## Considered and rejected

The spike ran each tool on the bundled schemas.

| Tool | Result |
|---|---|
| datamodel-code-generator (Python) | Good structs and real unions, but needs pydantic, and drops the raw JSON. |
| typify (Rust) | Good structs, `#[serde(untagged)]` unions, panics on the `not` keyword, drops the raw JSON. |
| go-jsonschema (Go) | Unions and the `type` constant become `interface{}`. |
| quicktype (all four) | Flattens every variant of a union into one struct with all fields optional. |
| NSwag / NJsonSchema (C#) | Fails on `$defs` references, and then on the root schema. |

Using the tools for structs and a script for the unions would leave four different pipelines, none of which keeps the raw JSON. One generator, with the behavior above written once, is smaller than that.

## Consequences

- A schema construct the generator does not know fails the generate task. Before any emitter runs, the model checks each schema file. A keyword must be modelled, an annotation (`$schema`, `$id`, `title`, `description`, `$comment`, `examples`, `deprecated`, `default`, `readOnly`, `writeOnly`), or one of two ignored forms, each with its reason recorded in the model:
  - `additionalProperties: true` or `false`, because decoders are tolerant readers that keep unknown fields. The model keeps `false` only to check union dispatch.
  - `not: {"const": "<string>"}` on a string property, as in `rawComponent`. The model keeps the excluded value only to check that a union's open-`type` variant excludes every tagged sibling; a decoder does not check it.

  Any other keyword or form, or a shape the model cannot express (a `type` array, an inline `oneOf` on a property, a boolean schema, an empty `enum`, a `$ref` or `allOf` cycle), fails with the schema file, the path inside it and the keyword. Two generated types with the same name (objects, enums and unions) fail with both sources. A new construct needs a change to the model and each emitter, with a test.
- The model decides how a union picks its variant, and fails generation unless every value valid for exactly one variant reaches that variant. Decoders try tagged and keyed variants in schema order and the open-`type` variant last. The rules:
  - A variant is listed once.
  - A variant whose `type` is a `const` is picked by that tag. It must require `type`, and no two variants may share a tag.
  - At most one variant has an open `type` (a `type` that is not a `const`, as in `rawComponent`). It is picked when nothing else matches, and must not accept any sibling's tag: a string `type` excludes it with `not: {"const": ...}`, so a union with an open `type` can have only one tagged variant; an `enum` `type` must not list it.
  - Any other variant is picked by a selector key: the first key by name that it requires and that no other variant has as a property, required or not. A variant with no such key fails.
  - A union with a keyed variant needs every variant closed with `additionalProperties: false`, so a key the schema does not name cannot appear in another variant's value.

  The error names the schema file, the `oneOf` index and the variants involved. The rules judge property names, tags and closedness; the schema's own `oneOf` and `task protocol:validate` still check that two variants never accept one value.
- The check assumes the schemas already pass the JSON Schema meta-schema check that `validate.py` runs in `task protocol:check`; a malformed keyword value can still crash the generator. It does not yet check that names are valid identifiers in each language, or that two names stay distinct after a language's casing rules.
- Decoders accept more than the schema allows. They keep fields a closed object does not name, and a variant decoded on its own does not check `not`. The schema and `task protocol:validate` stay the strict contract.
- Adding a language is one emitter, a round-trip test and a target in `generate.py`. The emitter maps the model's length unit to its host; a unit it cannot map fails generation.
- Python decoders take an already-parsed value. They are exact only on what `json.loads(text, parse_float=decimal.Decimal)` returns, which the replay uses; plain `json.loads` rounds a token such as `1.00000000000000001` to a float before the decoder sees it. `to_json` returns the numbers it was given: an unknown field keeps its `Decimal`, and a `number` field whose value still equals the original as a double writes the original back, so a value decoded from `Decimal` input encodes with a `Decimal`-aware writer. `json.loads` also differs from the Go, Rust and C# parsers in two ways. It accepts the tokens `NaN`, `Infinity` and `-Infinity`: an `integer` or `number` field holding one decodes as `Unknown`, but an unknown field keeps the float, and `json.dumps` then writes `NaN`, which is not JSON. It raises `ValueError` on an integer token over 4,300 digits (`sys.set_int_max_str_digits`). A caller reads wire text with `json.loads(text, parse_float=decimal.Decimal, parse_constant=reject)`, where `reject` raises `ValueError`, and treats `ValueError`, `ArithmeticError` and `RecursionError` from `json.loads` as text that is not a protocol message: `Decimal` raises `decimal.InvalidOperation`, an `ArithmeticError`, on an exponent it cannot hold (`0e999999999999999999999`), and deep nesting can raise `RecursionError` (20,000 levels did on Python 3.12 and 3.13 on macOS but not on the Linux CI runner; the limit depends on the platform's C stack).
- Rust decoders take a `serde_json::Value`, and the published crate does not enable `serde_json/arbitrary_precision` (feature unification would change `Number` for every downstream user) or `float_roundtrip`. So serde_json rounds a non-integer token to an `f64`, or refuses one out of `f64` range, before the decoder sees it. The replay records each such case as a documented Rust limit: `1.00000000000000001`, `9007199254740993.0`, `1e-29`, `1e1000000`, `1e-1000000`, `-9223372036854775809`, `1e400`, the `number` fields `9007199254740993.0`, `90.00000000000000001`, `0.30000000000000000000001` and `1e-400`, and the int64 maximum written as `9223372036854775807.000`, `9223372036854775807e0`, `9.223372036854775807e18` or `92233720368547758070e-1` (each read as 2^63, so `Unknown`). Also in the replay: the finite `number` `1.7976931348623158e308`, which serde_json refuses; a `number` above 2^64 (`18446744073709551616`), which re-encodes rounded; and the fractions `4611686018427387904.5` and `-9223372036854775807.5`, which serde_json rounds to whole doubles so Rust accepts them as integers. Not in the replay but the same limit: `1e-2147483649` and `0.` followed by 5,000 zeros and a `1` read as 0 and decode as the integer 0, and `1e2147483648` is refused. serde_json also refuses a lone surrogate. serde_json also refuses nesting beyond 127 levels by default; the replay lifts that with a test-only `unbounded_depth` feature so the decoder's depth rule is tested.
- C# `Decode` writes each message once and reads that output once to apply the depth, duplicate-key and Unicode rules, so it costs about two passes over the message where it used to read nothing up front. The writer replaces an in-memory lone surrogate with U+FFFD, so an escaped U+FFFD in the output sends the decoder back to the tree to tell the two apart. System.Text.Json can neither read nor write a string or key with a lone surrogate, so the `Unknown` value it returns for one keeps the field but cannot be written back (a documented C# limit). Repeated keys together with a lone surrogate give `Unknown` with no fields in C#.
- Go's `encoding/json` reads a lone surrogate as U+FFFD before the decoder sees it, so Go decodes such a message as if the text held U+FFFD (a documented limit).
- Schema changes show up as diffs in four generated files, reviewed with the schema change.
